## 核心判断

> 这套教程最有价值的地方，不是给出一批现成 prompt，而是把“如何让模型更稳定完成任务”拆成一套可训练、可复用、可组合的方法模块。

- 它把提示工程理解为“任务设计”，而不是“咒语收集”
- 它强调先把任务、输入、输出、约束、示例、推理路径说清楚，再追求语言上的技巧
- 它默认提示工程是可迭代的，要靠实验、对比和修正逐步逼近稳定输出
- 它的高级部分已经接近工作流设计：prompt chaining、tool use、search & retrieval

## 教程想教会的四种能力

### 1. 把模糊需求变成结构化任务

- 先说清楚要做什么，而不是一上来追求华丽表达
- 把角色、目标、材料、边界、输出格式拆开写
- 遇到复杂任务时，把“任务定义”放在“写答案”之前

### 2. 让输出结果更稳定

- 明确告诉模型输出什么，不输出什么
- 对格式敏感的任务，直接指定结构、标签或固定字段
- 需要高一致性的场景，不依赖模型“自己悟”，而是显式约束

### 3. 让模型在复杂任务里少走偏路

- 把材料和指令分开，减少串场
- 让模型先整理证据、再做判断
- 用 few-shot example 代替冗长抽象说明

### 4. 承认模型边界，并为边界设计补偿机制

- 不把模型当成天然准确的信息源
- 在高风险场景里要求引用、证据、复核
- 当纯 prompt 不够时，引入 chaining、tool use、retrieval

## 九章方法整合

## 第一章：Basic Prompt Structure

这一章在讲最小 prompt 骨架。核心不是复杂，而是完整。

最小可用结构通常包括：
- 任务指令：要模型做什么
- 上下文：模型完成任务需要知道什么
- 输出要求：答案应该长什么样
- 必要时的 system prompt：把全局规则前置

这一章的关键提醒是：如果 prompt 没把任务讲清楚，模型就只能靠概率补全你的意图。

### 可迁移方法

- 任何复杂任务都先回到“任务是什么、输入是什么、输出是什么”
- 先有骨架，再加技巧
- system prompt 适合放长期稳定规则，user prompt 适合放当前任务细节

## 第二章：Being Clear and Direct

这一章的核心观点很朴素但很重要：不要让模型猜。

清晰直接包括：
- 明确动作：总结、分类、改写、比较、提炼，不要混成一团
- 明确边界：只回答什么，不回答什么
- 明确长度、口吻、格式、角度
- 明确禁止项，比如不要写前言、不要额外解释、不要超出材料推断

### 它解决的失败模式

- 模型太“热心”，给了你没要的东西
- 模型理解得差不多，但差在最后 20%
- 输出看似对题，实际没有满足可交付要求

### 可迁移方法

- 与其说“帮我写一下”，不如说“基于以下材料，输出 3 条洞察，每条 1 句话”
- 与其事后改格式，不如在 prompt 里前置格式

## 第三章：Assigning Roles

这一章讲 role prompting，但真正有用的不是“扮演专家”本身，而是补上下文。

角色设定的价值在于：
- 给模型一个稳定视角
- 指定话语方式和受众
- 让回答更贴近使用场景

它还特别提醒一点：除了角色，还可以补“面向谁说”。同一个角色，对不同受众的表达完全不同。

### 可迁移方法

- 角色不是装饰，而是视角约束
- 更有效的写法通常是“你是 X，要向 Y 完成 Z”
- 如果角色不能提升判断质量，就不要硬加

## 第四章：Separating Data and Instructions

这是整套教程里非常关键的一章。

核心思想：
- 指令是指令
- 材料是材料
- 变量是变量
- 不要混在一起让模型自己分辨

教程特别强调：
- 做 prompt template 时，要让替换变量边界清楚
- Claude 对 XML tag 天然友好，适合拿来做分隔
- 小错误会放大，小 typo 也可能影响理解

### 推荐结构

```text
任务说明

<context>
这里放背景或规则
</context>

<data>
这里放待处理材料
</data>

<output_format>
这里放输出格式要求
</output_format>
```

### 它解决的失败模式

- 模型把用户输入的一部分误当成指令
- 模型分不清正文、注释、变量、任务描述
- 提示模板一旦换变量就失稳

## 第五章：Formatting Output and Speaking for Claude

这一章讲两件事。

第一件事是输出格式控制。  
不要等模型“自然输出成你想要的格式”，而要直接规定结构。

第二件事是 “speaking for Claude”，也就是通过 assistant prefill 预填开头，让模型从你指定的轨道继续写。

### 这一章的关键动作

- 用 XML tag 包住关键输出
- 用固定字段约束答案结构
- 用 assistant prefill 让模型跳过寒暄、前言和废话

### 适合的场景

- 需要稳定提取字段
- 需要模型直接进入正文
- 需要对接下游解析程序
- 需要强控论证起手方式

### 风险边界

- prefill 很强，但也容易把模型推得过死
- 适合格式化和轨道控制，不适合滥用

## 第六章：Precognition / Thinking Step by Step

这一章的核心不是让模型“多说一点”，而是让模型“按更稳的路径思考”。

适合使用 step-by-step 的任务：
- 分类
- 多步判断
- 数学或逻辑审查
- 先证据后结论的任务

### 关键理解

- 分步思考是降低错误率的手段，不是风格要求
- 有些任务需要展示过程，有些任务只需要内部走过程、最终只输出结论
- 推理链条越长，越要搭配格式控制

### 它解决的失败模式

- 模型直接跳结论
- 中间明明发现问题，但最后没修正最终判断
- 复杂分类任务里漏看条件

## 第七章：Using Examples

这一章讲 few-shot prompting。

它的核心价值是：很多时候，与其抽象描述“我想要什么”，不如直接给模型看“什么叫好答案”。

few-shot 特别适合：
- 风格学习
- 结构模仿
- 特殊格式输出
- 边界校准
- 告诉模型什么叫“不要这样做”

### 好用原则

- 示例要和目标任务足够相似
- 示例数量不需要多，关键是典型
- 最好同时给正例和反例
- 如果格式很重要，示例里就把格式做对

### 它解决的失败模式

- 规则都写了，模型还是抓不到“感觉”
- 风格飘
- 格式理解不到位
- 输出在边界附近频繁失误

## 第八章：Avoiding Hallucinations

这一章是从“写得像”走向“说得准”。

教程给出的几个关键抑制动作包括：
- 给模型留出口，允许它说不知道
- 让模型先找证据，再回答问题
- 在长文档场景里要求引用或定位依据
- 适当降低 temperature，减少发散编造

### 一个重要认知

模型幻觉很多时候不是“故意胡说”，而是它太想帮你把答案补齐。

所以抑制幻觉的关键不是单纯威胁它“不要错”，而是：
- 允许它承认信息不足
- 要求它把证据拿出来
- 把判断和材料绑定

### 高风险任务的推荐写法

```text
如果材料中没有明确证据，请直接回答“材料未提供”。
先列出支持答案的证据，再给出最终结论。
引用时尽量保留原句或位置标记。
不要根据常识补全材料中不存在的信息。
```

## 第九章：Building Complex Prompts

这是把前面所有方法拼起来的一章。

它强调的不是唯一模板，而是“复杂 prompt 是由多个元素组合出来的”。

常见元素包括：
- 角色
- 任务定义
- 目标受众
- 背景材料
- 输入数据
- 输出结构
- 质量标准
- 示例
- 禁止事项
- 复核动作

### 这一章最重要的观念

- 复杂 prompt 不必一开始就优雅
- 先把能用的元素都堆上，跑通
- 再慢慢删掉冗余部分，做瘦身

这其实是在教一种“prompt 原型开发”思路。

## 三个 Appendix 的方法价值

## Appendix 10.1：Chaining Prompts

核心思想：一次调用做不稳的事，可以拆成多次调用。

典型链路包括：
- 先生成，再审查
- 先列提纲，再扩写
- 先抽取信息，再组合输出
- 先做粗分类，再做精修

它适合：
- 复杂写作
- 长文档处理
- 需要复核的推理任务
- 需要从一个结果继续生长第二个结果的场景

## Appendix 10.2：Tool Use

这一部分本质上在讲：当模型本身做不到时，不要逼它硬做。

它把 tool use 拆成一个很实用的闭环：
1. 模型输出想调用的工具名和参数
2. 外部系统实际执行工具
3. 再把结果回填给模型继续生成

这个思路的关键不在“函数调用”这个词，而在于：
- 模型负责判断下一步需要什么能力
- 工具负责提供真实执行结果
- 模型再基于真实结果组织回答

## Appendix 10.3：Search & Retrieval

这一部分讲的是用检索来补模型知识边界。

核心目的：
- 让回答建立在外部材料上
- 提高事实准确率
- 让模型从“凭参数记忆作答”转向“基于检索证据作答”

对知识库、文档问答、研究型任务来说，这一步非常关键。

## 可以沉淀下来的提示工程原则

把整套教程压缩后，可以归纳成下面 10 条：

1. 先定义任务，再要求表现
2. 指令、材料、变量必须分层
3. 输出格式要前置，不要事后补救
4. 角色的价值在于视角，不在于花哨
5. 复杂任务优先分步，不要一口吃完
6. 规则讲不清时，用示例校准
7. 高风险任务先找证据，再下结论
8. 允许模型承认“不知道”比强迫全答更稳
9. 单轮 prompt 不够时，改用 chaining
10. 需要外部事实或执行能力时，就接工具和检索

## 常见失败模式与修正策略

| 失败模式 | 常见表现 | 更稳的修正方式 |
|---|---|---|
| 任务不清 | 回答沾边但不对题 | 明确动作、边界和交付物 |
| 指令和材料混杂 | 模型串场、误读输入 | 用 XML tag 或分段结构隔开 |
| 输出漂移 | 格式不稳、字段丢失 | 明确 schema、标签或模板 |
| 风格不准 | 像 AI 套话 | 给 few-shot 正例和反例 |
| 推理跳步 | 中间发现问题，结论没改 | 让模型先分步检查再作答 |
| 长文档幻觉 | 把干扰信息当答案 | 要求先抽证据、再回答、再引用 |
| 单轮过载 | 任务太长太杂 | 拆成 chaining 流程 |
| 能力边界碰壁 | 算错、查错、执行不了 | 把问题转给工具或检索层 |

## 对当前工作空间的迁移启发

这套教程对当前工作空间最直接的价值，不是替换已有 skill，而是补强其提示协议。

### 对 `prompt-flow`

- 可以把“任务分类”继续升级成“失败模式诊断”
- 每类任务都可固定成：目标、输入边界、输出格式、质量标准、禁止事项、示例

### 对 Wiki 的 `Ingest / Digest / Query / Produce / Check`

- `Ingest`：最适合强化“材料与指令分离”
- `Digest`：最适合强化“证据先行”
- `Query`：最适合强化“格式化输出 + 引用”
- `Produce`：最适合强化“提纲 -> 展开 -> 质检”的 chaining
- `Check`：最适合强化“幻觉检查 + 来源核验”

### 对 `hv-analysis`

- 可补入“事实 / 推断 / 假设”三层区分
- 可把横向对比维度固定成更强的 schema 输出

### 对 `oral-copy` 与 `khazix-writer`

- 可引入更明确的 few-shot 风格示例
- 可把风格规则从“抽象要求”升级成“规则 + 正反例”

## 一份可复用的最小提示骨架

```text
你要完成的任务：
{TASK}

任务背景：
<context>
{CONTEXT}
</context>

待处理材料：
<data>
{DATA}
</data>

输出要求：
<output_format>
{OUTPUT_FORMAT}
</output_format>

质量要求：
- 只基于给定材料作答
- 如果证据不足，明确说明“材料未提供”
- 不要输出与任务无关的前言或寒暄
```

## 实践清单

- 先问：我到底要模型做什么
- 再问：输入材料和规则有没有混在一起
- 再问：输出是不是已经被我定义清楚
- 再问：这个任务更适合规则说明，还是 few-shot 示例
- 再问：我需不需要模型先收集证据再回答
- 再问：这件事单轮能做稳吗，还是要拆链
- 最后问：这里是不是已经超出模型裸能力，应该接工具或检索

## 相关概念

- 提示工程的本质更接近“任务编排”而不是“魔法措辞”
- 复杂 prompt 的上限，往往取决于结构、证据和工作流，而不是修辞
- 这套教程适合作为任何 skill 的底层 prompting 训练教材
